## Amendment 2026-10-13: retroactive preflight backtest (M12 workstream 3)

Written before the backtest's first run; no backtest number existed when this was written.
- **Question:** would the pre-deploy gate have flagged the historical PRs whose deploys caused incidents, and at what cost in flagged PRs?
- **Population:** every merged `(:PR)` with `merged_at` in `golden_acme` and `golden_globex` (read-only, RO wrapper). A PR is *incident-causing* when `(:PR)-[:CONTAINS]->(:Commit)<-[:CONTAINS]-(:Deploy)-[:CAUSED]->(:Incident)` exists. Labels come from graph history, not from `*.truth.json`.
- **No future:** each PR is scored as of its `merged_at`. Past incidents count only if opened before it; runbooks, ownership (OWNED_AT windows), commit counts and team membership (bus factor) are read as of the same instant. Topology (blast, revenue, betweenness) is not time-versioned and is read as it is now.
- **Scoring:** the production preflight scoring function and `weights.yaml` unchanged. **No weight or threshold is tuned on backtest results.**
- **Metrics per tenant:** catch rate (causing PRs with verdict block or require_review), block rate and review rate over all PRs, the same split into the first and last third of the merge-time window, a confusion table, and AUROC of risk (causing vs not).
- **Ablation:** the same metrics with the past-incidents term weighted 0 (structure only), to show how much comes from memory.
- **Reported whatever they turn out to be**, with the limits: synthetic data; incident causes drawn from per-archetype component lists (the past-incidents term is partly self-fulfilling); historical PRs carry no ChangeFacts, so the decision term cannot fire.

## Amendment 2026-10-13: model-mismatch robustness and a telemetry-only arm (prejudge review)

Written before either was run or coded beyond a stub. Nothing below has been tuned on a result.

- **Why.** Every earlier gate number was measured on worlds whose telemetry was generated over the same topology and capacities the gate reads (the simulator propagates along `PROPAGATES_TO.cap`). That is a test of consistency, not of robustness to a wrong graph.
- **Model-mismatch eval (`evals/mismatch_eval.py`).** The 100 held-out gate-bench worlds (seed 20261015), each prepared as usual (the world's telemetry is generated from the TRUE topology), then the graph the product reads is made wrong, per case with a seeded stream (case seed XOR 0x313), in four variants run separately:
  - `caps`: every `PROPAGATES_TO.cap` multiplied by U(0.5, 1.5), clipped to [0.01, 1.0];
  - `hidden`: one random `PROPAGATES_TO` edge deleted from the graph (the world still propagates over it);
  - `stale`: one `PROPAGATES_TO` edge added between two components with no edge, that does not create a cycle, cap U(0.1, 1.0) (the world has no such edge);
  - `all`: the three together.
  Graded with the gate bench's own expected verdicts and grader (unchanged). Reported per variant: correct k/n, **wrong-confident** (a CONFIRMED outcome blaming a change other than the expected cause, or any blame where the expected outcome is an abstention or no incident), abstention (no change blamed, outcome NOT_CONFIDENT or UNKNOWN_ESCALATED), and the cases that flipped from correct to wrong. **Expectation stated now:** accuracy drops; the safety property under test is that wrong-confident stays at or below 5% of cases in `caps`. `hidden`, `stale` and `all` are reported whatever they show, with no threshold.
- **Arm T, telemetry only (no topology).** In the scenario clean room: among the changes in the alert window (the same list arm N reads), blame the one whose own component shows the largest measured excess (peak error rate since onset minus its pre-onset mean, from its MetricWindows); ties scored 1/k like arm N; it never abstains. Scored with the same top-1 / false-blame / abstention metrics as the other arms. It answers "does a plain anomaly heuristic already solve these scenarios?". Reported whatever it shows.
- **Arm T on the gate bench too** (added after arm T's first scenario trial and before any bench run of it): the 100 held-out bench worlds, each prepared as usual, graded with the bench's own expected verdicts: correct (blamed the expected cause on a confirm case; T cannot abstain, so every abstain and control case is a wrong blame). Reported next to the product's bench numbers.

## Amendment 2026-10-13: memory that changes the answer, a learned edge after a verified fix (M15 #4)

Written before the mechanism or the eval was run.
- **Mechanism.** When an incident's rollback of change C (on component O) is verified APPLIED and the graph has no PROPAGATES_TO path from O to the incident's symptom S within the gate bound, Faultline PROPOSES a learned failure edge O → S with capacity = the measured share (S's excess / O's excess in that incident's windows, at most 1). A human approves it two-step (plan hash). Only then is `PROPAGATES_TO {learned: true, from_incident, approved_by}` written. The gate is unchanged: a learned edge is an edge, named in the proof path.
- **Eval (`evals/learning_eval.py`), sequential.** The held-out bench worlds with a true cause (G2, G5 and origin categories, seed 20261015). For each: delete one PROPAGATES_TO edge ON the cause → symptom path from the graph the product reads (the world keeps it: variant `hidden_on_path`). Incident 1 runs: graded abstain / correct / wrong-confident. The eval then plays the human: rolls back the true cause, verification decides; if APPLIED and a proposal is made, it is approved. Incident 2: the same world, a new deploy on the same component, the same distractors re-injected, graph = the learned graph. Reported: incident 1 abstentions and wrong-confident; proposals made; incident 2 correct, wrong-confident; and the control: incident 2 with nothing learned. **Expectation stated now:** incident 1 wrong-confident 0; incident 2 correct rises above the control; wrong-confident stays 0. Reported whatever it shows.
- **Addendum (written after the first learning runs, before this arm ran).** The first runs verified the human fix on the product's own (wrong) graph, so any rollback looked like a fix; verification now simulates over a copy of the TRUE world (`act.verify(world_graph=…)`), a live test pins it, and the 24/24 result was re-measured with it. Added arm, **wrong guess**: in a second room of each case the human names a decoy (the first eliminated distractor) instead of the cause. Expected: verification NOT_APPLIED, no proposal, no learned edge, in every case. Reported whatever it shows. Also disclosed: a human fix was first allowed only from UNKNOWN_ESCALATED and AWAITING_APPROVAL; after the first run (6 not-confident incidents could not take one) it is also allowed from GATE.

## Amendment 2026-10-14: the deep bench (multi-hop causes and downstream look-alikes)

Written before `evals/deep_bench.py` was coded or run. Nothing below has been tuned on a result.

- **Why.** The robustness/depth eval showed every held-out bench cause is 0–1 hops from its symptom (by construction: a symptom is the cause or a direct synchronous client), and no bench decoy ever sits *downstream* of the cause. The graph's claim, that multi-hop context matters, was therefore untested, as was the most common real trap: a deploy on a component that is erroring only because something upstream broke.
- **Worlds.** Generated from the same topology config (oracle code over `data/topology/otel-demo.yaml`, never the engine), seed **20261014**, never used before. Visible chains = synchronous calls (cap 1.0) with call share ≥ 0.4, the bench's own visibility rule, followed hop by hop. Two categories, 20 cases each:
  - `deep_onpath`: the cause on a component, the alert on a component 2–4 visible hops downstream, and a look-alike deploy on a component strictly between them on such a chain (plus 0–1 no-path decoy).
  - `symptom_decoy`: the cause 1–4 visible hops upstream of the alerting component, and a look-alike deploy on the alerting component itself (plus 0–1 no-path decoy).
  Effect sizes, world seeds, decoy choices and opaque ids drawn as in `gate_bench.py`; same-minute deploys; one alert.
- **Expected verdict (fixed by the generator):** CONFIRMED, the upstream cause blamed, every decoy eliminated. The bench expects downstream look-alikes eliminated by G4 (origin) and no-path decoys by G2; the gate that actually eliminated each decoy is reported, not required.
- **Primary metrics:** right cause blamed (k/40), wrong-confident (a confirmed blame of any other change), abstentions; by category and by hop distance. **Comparator:** arm T (telemetry only: the window's change whose component shows the largest error-rate excess; ties scored 1/k) on the same worlds.
- **Expectation stated now:** the gate blames the right cause in most cases with 0 wrong-confident; arm T is near chance between the cause and the downstream look-alike, which inherits the cause's excess. Reported whatever it shows; any gate fix prompted by it is logged and the bench re-run on a fresh seed as well.
- **Addendum 1 (2026-10-14, after the first run, before any gate change was run):** the first run blamed the right cause in 0/40 (every case escalated: the downstream look-alike survives every gate because it is genuinely anomalous), with 0 wrong-confident; arm T 34/40. A gate rule is being added (G4 upstream-explained: a suspect whose measured excess is no more than what another anomalous suspect upstream can carry to it is not an origin). Because that rule makes the gate eliminate more, a third category is added **before the rule is run**, as its adversarial test: `abstain_downstream` (20 cases): a component degrades with **no** change on it, and 1–2 look-alike deploys sit downstream of it (on a visible chain to the alerting component, or on the alerting component). Expected: abstain (no change blamed). Wrong-confident on this category is the safety metric for the new rule; it is reported for the gate before and after the rule. The fixed gate is also re-run on a fresh seed (**20261016**) of all three categories, never looked at before.
- **Addendum 2 (2026-10-14, after an adversarial review of the G4-upstream rule, before the redesigned rule or these categories were run).** The review reproduced four hand-built worlds where the rule as first shipped (upper-bound transfer summed over paths and capped at 1, × slack 1.25, peak values only) turned a safe escalation into a confident wrong blame. Four adversarial categories are added to the deep bench, 20 cases each, generated from the same config with the same seeds, and graded so that **any confident blame of a change other than the expected one is wrong-confident** (the safety metric):
  - `two_causes_chain`: two changed components u → s on a visible chain, each with its own fault (u 0.25–0.6; s's own 0.10–0.30), alert on s. Expected: no confident blame (multi-cause → not confident).
  - `weak_link`: the changed alerting component s has its own fault; a changed component u with its own fault reaches s only over paths with a low-share hop (call share < 0.4: not visible). Expected: s's change confirmed, or an abstention; blaming u confidently is wrong.
  - `late_upstream`: s changed with its own fault from −2m; a changed component u upstream on a visible chain faults from 0m (after s). Expected: s's change confirmed, or an abstention; blaming u is wrong.
  - `noisy_upstream`: s changed with its own fault (alert on s); an UNCHANGED component upstream on a visible chain also faults from −2m. Expected: s's change confirmed, or an abstention; blaming anything else is wrong.
  The redesign to be measured (stated now): (1) a downgrade-only confirm check: a confirmed change whose components' excess an anomalous upstream component could carry under the generous upper bound is not confident; (2) elimination in the sweep only under a strict lower bound: upstream excess × the best single path's product of cap × call share (the call share the graph records on each edge), no slack, and the upstream anomaly must start no later than the suspect's; each elimination records its measurements as evidence. Reported for the first-shipped rule and for the redesign, all seven categories, dev and fresh seeds.

## Amendment 2026-10-14: M16 context packs and procedural memory

Written before either feature or its eval was coded. Nothing below has been tuned on a result.

- **Context pack eval (`evals/context_eval.py`).** Worlds with grader truth: the scenarios' `*.truth.json` (cause change, causal chain, responders, violated decisions, runbook where given) and the cause worlds of the held-out gate bench (seed 20261015) and of the fresh deep bench (seed 20261016), whose truth is the generator's: the cause change, its component and the oracle chain to the alert (grader code over the topology config, never the engine). For each world, three packs answer the same input (the alert text, as INTAKE receives it), each cut to the same budget of 500, 1,000 and 2,000 tokens (tokens counted as characters / 4 on the serialised pack, one rule for all):
  - **G**: the product's `context_pack`;
  - **V**: vector RAG over the same items. Every item G could include is serialised to text the same way, embedded with the product's embedding model, and taken by cosine similarity to the input, top-down until the budget is used, plus a one-paragraph text description of the topology;
  - **R**: recency. The window's changes and alerts newest first, then the topology description, to the budget.
  Metric: recall of each truth item (cause change, cause component, every chain node, responder, decision, runbook) per budget; whether the cause change is present at all; pack build time p50/p95. **Expectation stated now:** G ≥ V and G ≥ R on cause and chain recall at every budget; V may match G on responders and runbooks, because those are textually similar to the alert. Reported whatever it shows.
- **Procedural memory eval (`evals/procedure_eval.py`).** Families of two incidents with the same alerting component and the same cause component but different world seeds and decoys: the scenario repeats already used (S1→S1b, S3→S3b), plus 20 generated families (gate-bench generator rules, seed **20261017**, never used before). Incident 1 runs cold, its fix is verified and its procedure written back; incident 2 runs warm, and also cold on a separate copy as the control. Metrics: tool calls, graph queries and wall time to the gate's verdict, warm vs cold. Verdicts must be identical (same outcome, same cause, same eliminations), and any difference is a failure. Wrong-confident must be 0. **Expectation stated now:** warm uses at least 30% fewer tool calls with identical verdicts. Reported whatever it shows.
- **Addendum 1 to the context-pack eval (2026-10-14, after its first run, before this was run).** First run (110 worlds: 5 scenarios, 65 gate-bench, 40 deep-bench): the eval barely discriminates. These worlds hold one to three changes in the window, so every pack fits nearly everything. The cause was in G, V and R alike in about 99% of worlds at every budget; G led only on constraining decisions at 500 tokens and on responders vs R. One G miss (S2) was a product bug: the pack used the default 30-minute window instead of the incident's own (S2: 60), so a cause 40 minutes before onset was outside it. Fixed (`context_pack(window_min=…)`, passed by the eval exactly as the product's run receives it) and disclosed. **Busy-window knob, added now:** every world re-run with k extra deploys in the window, k ∈ {10, 30}. Each goes on a component drawn with a seeded stream (world id), at a uniformly drawn minute in [−29, −1], titled like the bench's ("<component>: change"). This is the condition context engineering exists for: dozens of deploys across the org. Same metrics and budgets. **Expectation stated now:** at k = 30, G keeps cause recall at 500 tokens ≥ 0.9, while V and R drop well below it. Reported whatever it shows.
- **Addendum 2 to the context-pack eval (2026-10-14, after the busy-window run, before this was run).** At k = 30 extra deploys and 500 tokens: cause in G 0.99, V 0.78, R 0.99. Two findings.
